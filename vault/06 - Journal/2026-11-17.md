  - `mod-api-port` cannot build either: it needs an SDK, and no Nightly with the mod API (so no SDK) has been published.

## 🧠 Learned / found
- A launcher release can carry the mod API before any Nightly does: the launcher and the game are released separately, and native mods compile against the Nightly's SDK, not the launcher.
- `ext/horizon` may be a sparse checkout: `tools/link-sdk.ps1` then fails ("no crates\horizon-mod-api"); `git sparse-checkout disable` fixes it.

## ⚖️ Decisions made
- No merge of `mod-api-port` into `main` yet: ADR-018's trigger is the first **Nightly** with the mod API and its SDK, not the launcher.

## Later: launcher 0.2.71
- Bastien pasted the notes of **launcher 0.2.71** (`3f1843e`): only two fixes, Chinese translations (#17805) and "Play starts a Java Edition instance again" (#17975, fixes #17950). It is 130 commits past the mod API merge; nothing new for native mods. `horizon-launcher versions` still lists `nightly-2026-11-13-9f42064` as the newest Nightly.
- **The launcher updates itself**: the dev PC was already on 0.2.70 without anyone installing it (`horizon-launcher --version`). So "keep 0.2.69 for tests" only holds if the update is held back; in practice an up-to-date launcher builds neither branch until the Nightly. A build made before the update (the instance's `native-...` version) is left alone; whether Play still starts it without a rebuild is untested.
- Read `launcher/src/native_mods.rs` at `launcher@0.2.71`: `pipeline` builds on `build_revision(base, ..)`, the revision of the installed version the instance plays, and **refuses any mod pinning another revision** (`MISMATCH`: "Made for other Horizon versions: ...; rebuild against this game"). The doc comment says "on the Horizon revision they pin", but the code does not fetch a mod's own pin to build on. So when the Nightly ships, `mod-api-port` must be re-pinned on it (`cargo horizon-mod update`, already in the plan) before any build; the `c07bfa7` pin alone is refused.
